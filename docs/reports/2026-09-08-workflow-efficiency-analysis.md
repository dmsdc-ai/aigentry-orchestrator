## 3. 측정하지 못한 범위

- **워커 내부의 작업/유휴 비율** — 워커 세션 턴 로그 미보존. 이 때문에 워크플로우가 유휴 병목인지 아닌지 자체를 판정하지 않았다(§0).
- **단계 완료 시점** — dispatch 80건 전부 `outcome.state=unknown`. 어떤 태스크가 언제 실제로 끝났는지 기록이 없다(F5).
- **중복 통지·bookkeeping의 과금 토큰 증분** — input의 97.2%가 캐시 적중이라 컨텍스트 크기 × 왕복 수 곱셈은 성립하지 않는다. 왕복 횟수만 셌다(F3, F6).
- 08:00~18:50 HOLD 유실은 #1128에서 진단 완료된 **과거 문제**다. 오늘 21:01 이후 shared ref 22건은 전부 대응 turn이 확인되며, 전달 유실은 재현되지 않았다.
- 토큰 비용 환산, CLI별 처리 속도 비교. 산문 길이로 비용을 추정하거나 겹치는 wall-clock으로 인과를 추정하지 않았다.

## 6. 이 감사 자체의 비용 (요청된 자기 평가)

비용: 세션 1개, ref 6,387바이트, 보고서 1건, 검토 1라운드. **위임은 정당했다고 본다.** (1) 오케스트레이터 자신이 감사 대상이라 자기 보고로는 F2의 28초 순서 역전과 F3의 템플릿 근거를 확정할 수 없었다 — transcript tool call 순서와 소스를 직접 읽어야 나온다. (2) 오케스트레이터 컨텍스트는 이미 요청당 203K였고 transcript 704행·원장 1.9MB를 더 읽으면 압박이 커진다. (3) 오케스트레이터가 21:49:50에 제시한 5건 중 "승인 반복"은 부분 기각, "직렬화"는 기각됐다.

**단, 이 감사의 1차 초안은 네 군데를 과잉 주장했고 검토에서 걸러졌다**: 지시 보유 구간을 가동률로 읽어 "유휴 병목 아님"을 결론지은 것, 문자 수와 토큰을 비교해 "출력의 2/3" 를 주장한 것, 캐시 적중을 무시하고 60만 토큰 증분을 계산한 것, 세션 부재만으로 태스크 단계 완료를 단정한 것. **감사자에게도 §2의 "판정 불가" 칸이 필요하다는 것이 이번 라운드의 실제 교훈이다.** 검토 라운드는 절약분을 상쇄한 것이 아니라 잘못된 수용 기준이 #1136에 흘러드는 것을 막았다.

§4 수용 신호를 그대로 #1136 구현 기준으로 쓸 것을 권한다 — 단, 각 신호는 근거가 되는 기록(transcript tool call 순서, ref mtime, `telepty list`, `active.json` lifecycle)에서 직접 세는 것이어야 하고, 추정으로 채우지 않아야 한다.
