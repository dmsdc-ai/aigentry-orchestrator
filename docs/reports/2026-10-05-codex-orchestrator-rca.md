## 가설 검증 (교체 오케스트레이터의 초기 추정 7개)

- 기각: "거대한 툴 출력이 컨텍스트를 터뜨렸다" — 1 MB 이상 출력이 모델에 들어간 적 없음. 압축은 자연 충전(258k 창의 245k에서 발동).
- 부분 기각: "설계 질문이 모든 경로를 막았다" — 질문은 비동기라 dispatch는 계속됐다. 전체를 세운 것은 자기 규칙 예외 요청과 로그인 갱신 질문이었다.
- 수정: "범위가 계속 늘었다"는 맞지만 원인은 사용자 요청(범위 추가 56건, 축소 1건, 09-13 분할 출하 거절)이다. 오케스트레이터의 잘못은 비용을 수치로 보여주거나 축소를 제안한 적이 한 번도 없다는 것(0건).
- 지지: 절차 과다, 완벽주의, 규칙 충돌, 읽기 어려운 노트.

## 규칙 충돌 (원문 인용은 B 보고서 §6.4)

1. "기술 결정은 자율 판단, 사용자에게 묻지 않는다" (공통 CLAUDE.md) ↔ Rule 30 표 "Architecture / design decision = 사용자", Rule 24/47 "새 아키텍처는 승인"
2. Rule 32 "즉시 workaround (required)" ↔ Rule 27 "증상을 우회하지 않는다"
3. 역할 지침 "fire 전 항상 confirm" ↔ Rule 6 "같은 범위에서 재확인하지 않는다"
4. Rule 4 "직접 수행 금지" + Rule 46 "격리 검증 못 하면 스폰 거부" → 스폰 경로가 고장 나면 교착
5. "fix 루프에서 /clear 금지" ↔ Rule 12 "구현 위임 전 반드시 /clear"

규칙 스택은 8개 파일 192 KB(약 4.7만 토큰), 번호 규칙 56개 중 40개가 "멈춤" 게이트, dispatch 1회당 체크 항목 51개.

## 권고 교정 조치

1. **릴리스 형태를 게이트로 고정**: 10-05 결정(검증분 먼저 출하)을 Rule 45/50에 반영 — "출하 조각"을 유효한 종료 상태로, "full scope retained / no waiver" 문구 삭제. 새 요청은 기본적으로 다음 릴리스 백로그로.
2. **권한 규칙을 한 문장으로**: 기술 선택은 오케스트레이터, 사용자 승인은 비용·개인정보 이동·권한 확대·운영 데이터 변경/삭제·프로덕션 배포만. Rule 30 표의 architecture/verdict/commit 행과 "fire 전 항상 confirm" 삭제. Rule 4에 자기수리 예외(워커를 못 띄울 때 dispatch·격리 코드 직접 수정).
3. **결정 큐 하나 + 기본값**: 열린 질문을 한 파일에 권고안·막힌 작업·기한과 함께. 기술 항목은 기한 후 권고안 적용.
4. **절차를 크기에 비례**: 20줄 이하·테스트 전용 변경은 코더 1명 + CI가 검증자. 체크리스트 51 → 10 이하. dispatch 결과를 기계가 판정(현재 전부 unknown). 워커 수명주기를 명령 1개로.
5. **상태·런타임 위생**: 태스크 큐를 태스크별 파일로(현재 5.2 MB 단일 파일, 2,403회 재작성), 노트는 읽을 수 있는 문장으로, 릴리스/일 단위로 새 오케스트레이터 스레드, 로그인 만료 사전 경보.
