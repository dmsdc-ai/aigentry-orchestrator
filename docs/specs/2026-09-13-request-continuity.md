## Single continuity contract

1. New unrelated requests and status questions are additive. Focus, report phase, clean exit, compaction and elapsed time cannot cancel an assignment. Persist immutable original plus explicit revisions; never replace the original with a summary or later prompt.
2. Extend existing dispatch/inbox persistence with original/evidence objects and receipt metadata; keep task-queue as the task projection and registry as dispatch authority. Do not add a scheduler or second task ledger. Task Loop remains OFF absent explicit activation; Advisor only proposes (src/task-advisor/contracts.ts:1 explicitly says validation does not authenticate).
3. Required adapter call: receiveSubmittedInput({channel, upstreamNamespace, upstreamDeliveryId|null, rawBytes, mediaType, conversationId, provenanceEvidence|null}) before model consumption/acceptance response. Native adapter must supply submitted input, not reconstruct keystrokes or scrape screen text; raw fidelity and delivery coverage must be measured per channel.
4. Store one locally generated capture_id per observed delivery, byte length, SHA-256, original_ref, durable store owner/workspace, channel, upstream namespace/ID, received_at and provenance status. Copy original bytes into owner-only immutable storage before acceptance; an external/shared mutable path alone is insufficient. Equal bytes may share a blob but have separate delivery/request records.
5. Real upstream identity keys idempotency: same namespace+delivery_id returns same receipt; identical text with different IDs remains intentionally repeatable; same ID with conflicting digest is a visible identity conflict. A local UUID, filename, byte offset, new text/hash or timestamp cannot establish upstream redelivery identity or new authority. Null upstream ID means upstream deduplication unavailable; never suppress by content.
6. received means a hook observed an event, with capture availability stated; it promises no durability. accepted means exact original and receipt committed durably, even if task projection is pending; it is evidence acceptance, not execution authorization. unknown means receipt/delivery/completion cannot be proved; preserve facts and the missing-evidence reason. Uninstrumented events are not labelled received.
7. Transaction order: persist immutable bytes → fsync file and required parent creation/rename metadata → serialize receipt mutation on stable lock → commit receipt with original digest and pending projection → durable-acceptance ACK → task binding/projection. ACK contains capture_id, digest, upstream identity availability and admission state. Crash before ACK permits receipt lookup/retry, not a guessed successful ACK.
8. Use atomicWrite + withIndexLock (src/session/persistence/atomic-write.ts:81; index-lock.ts:87) for TS receipt/cursor writers and existing bin/dispatch-registry.py _Lock/commit (:160,:256) for registry mutations. Every writer of a shared projection must join the same transaction protocol; tmp+rename alone is not serialization. No new dependency. Existing Python registry remains reused; native TS helpers supply the core-only path for TS-owned records.
9. Do not blindly reuse weaker helpers: telepty saveTrackedInjections:184 swallows directory-fsync errors; sessions save/load (:71,:80) swallows errors and stores metadata only. TS atomicWrite skips directory fsync on Windows. Supported-filesystem guarantees must be measured; unsupported durability becomes explicit capability limitation, not POSIX-equivalent ACK. sweepIncompleteWrites (:15,:38; hash a5f99ef86749) deletes matching temps without owner checks: exclude continuity/in-flight artifacts and do not call it as request recovery.
10. ENOSPC/EACCES/corruption/fsync failure produces visible acceptance-pending or refusal, preserves existing bytes and refuses an acceptance ACK. Never reset a corrupt receipt store to empty. Crash after object write before receipt leaves recoverable unindexed evidence, not admitted work; reconcile inventory under the same owner lock. A failed projection cannot erase a committed original.
11. Bind accepted request_id + revision_id + admission_ref to existing task_id and exact {sid, session_epoch|null, worker_attempt, dispatch_id, operation, scope_revision}. Distinguish unknown values explicitly; backfill only from measured manifests/delivery evidence. Registry begin-delivery must persist these links before dispatch; task projection can recover idempotently from them. A missing binding means waiting for reconciliation, never a fresh assignment.
12. Each revision links parent_revision and its immutable original_ref. Pause/cancel/replace requires an authenticated decision envelope {decision_id, actor proof, target request/revision/task/attempt/operation, expected scope_revision, action, admitted scope}; controller validates it with the existing authority/HITL owner. Missing/mismatched/stale proof leaves only that dependent work waiting. Replacement preserves previous artifacts and affects only named targets; unrelated work continues.
13. Absence of inject markers, body.from, a model/tool message, JSON status/done or a verified machine SID cannot prove human intent. The current controller receives both human and machine messages; human decision provenance must come from a positively authenticated upstream channel. Replay must recheck existing admission, current scope, sandbox, budget and unresolved HITL; persistence grants none of them.
14. Checkpoint references belong to the exact binding and include original/revision refs, next action, owner, resume condition, uncommitted artifact paths/digests at observation time, source revision/worktree and outstanding delivery/REPORT/ACK IDs. Preserve mutable partial artifacts in place with their owner; no forced commit, reset, deletion or transcript-wide copying. Digests identify observed bytes, not later file contents.
15. Report state is received → original durably filed → exact attempt correlated → controller verification recorded → acceptance ACK durably owed → ACK delivered/acknowledged. Retain report bytes and retry obligations across any cut. A legacy REPORT or filename classification is evidence awaiting review; phase completion never retires the original assignment. ACK loss causes idempotent re-ACK, never repeated work.
16. On restart, next turn after compaction and wake, enumerate accepted receipts/pending projections, then join exact task/dispatch/report/checkpoint records. First classify each attempt as active, delivery-unknown, report-awaiting-verification, verified-complete, or explicitly paused/cancelled; expose missing links separately. Drain report/ACK obligations before considering work resumption; do not redispatch unknown completion (including src/reconciler/cli.ts:519's existing --no-task recovery path).
17. Resume only already admitted, nonterminal work with valid exact binding and current execution constraints. Active workers receive checkpoint/decision follow-up only under their existing admission; unknown workers remain protected until resolved. Cleanup must consult exact attempt + HITL + report obligations and preserved artifact ownership before kill/close/removal, including old legacy-source scheduled entries. Failure in one request cannot block unrelated admitted work.
18. Existing tq-status/tracker views project received/pending/running/waiting/verified-complete/explicitly-cancelled with reason, owner, resume condition, receipt state and capture/provenance limits; paused is waiting with explicit decision. No terminal-dependent truth store. Received is displayed only when observed, and verified-complete requires controller verification of the exact revision and attempt, never screen text or transport success.
